## (b) Responder analysis

**22 distinct WhatsApp numbers** carried a broadcast-recipient row with `status=replied` in the
window (27 `replied` rows total across templates — a few numbers replied to more than one send).
Pulling each of those 22 numbers' `getMessages` history and filtering to inbound
(`owner=false`, `eventType=message`) messages timestamped inside the study window found **45
in-window inbound messages** from those 22 numbers. Response-mode breakdown (by message):

| Mode | Count | Notes |
|---|---:|---|
| Quick-reply button tap | **18** | text exactly matches a known template quick-reply label (see Appendix method) |
| Keyword trigger | **1** | text matches the 6-char letter-start alphanumeric `client_id` pattern (`apps/referrals/validators.py` convention) |
| Free text | **26** | everything else (greetings, unrelated spam/broker messages, stray characters) |
| URL-button click | **not measurable** | see below |

**URL-button clicks are not observable from Wati for this tenant** — every template's
`isUrlBtnClickTrackingEnabled` flag is `false` in the live template list
(`.run/t031/templates_full.json`), so Wati records no click event for the "Share on WhatsApp" /
referral-link buttons at all. The only available proxy is GoRefer's own `/share/wa/{client_id}`
`SHARE_INTENT` event stream — see (d).

**Parser-reality note:** a tapped quick-reply button does NOT arrive in `getMessages` as a
structured `buttonReply`/`interactive` object in this tenant's data — it arrives as a plain
`eventType="message", type="text"` row whose `text` field is the exact button label
(verified against 2 real captured payloads, `text="Refer & Earn"` and `text="Talk to advisor"`,
both with `buttonReply: null, interactive: null` — quoted verbatim in the run progress log).
Classification is therefore a text match against the button-label set extracted from
`templates_full.json`, not a structured-field check.

**22 responders out of 1,970 distinct recipients contacted in-window = 1.1% distinct-responder rate.**

## (c) 24h session windows opened — cross-checked

Two independent counts, deliberately shown side by side (they disagree — see Finding below):

| Source | Metric | Count |
|---|---|---:|
| `ScheduledFollowup` (`apps/followups`) | distinct `(mobile, window_opened_at)` pairs with `window_opened_at` in-window | **4** |
| `ScheduledFollowup` | total scheduled-followup rows created off those opens | 22 |
| `FollowupWindow` (`apps/followups`) | rows whose `last_inbound_at` falls in-window | **2** |
| `FollowupWindow` | total rows in the table (all-time) | 2 |

**Finding — the two counts disagree by design, not by data error.** `FollowupWindow` is a
**current-state** table with a `UniqueConstraint` on `(tenant, mobile)` — each new inbound
overwrites `last_inbound_at` on the SAME row rather than appending history, so it can only ever
show the LATEST window per contact, not how many times a window opened within the study period.
`ScheduledFollowup.window_opened_at` is stamped at enqueue time (once per fresh open, per
`apps/followups/tasks.py::enqueue_followups`) and is never overwritten, so it is the more accurate
historical count: **4 distinct window-opens** in the study window (against only 2 unique mobiles
ever recorded in `FollowupWindow` — meaning at least one contact's window opened, closed >24h, and
re-opened within the 7-day study period, an event `FollowupWindow` cannot show).

## (e) Why interaction is low — hypotheses tied to the data above

1. **The per-user marketing cap (Meta 131049) is silently discarding over a fifth of every send.**
   407 of 682 failures (59.7%) and 407/2,047 (19.9%) of ALL sends in the window failed with
   131049 — Meta enforces a hard per-recipient cap on MARKETING-category template volume, and
   1,991 of 2,047 sends (97.3%) in this window are MARKETING (section a). A recipient who has
   already hit the cap this cycle receives NOTHING, and cannot reply to a message that never
   arrived — this alone could fully explain a large share of the low reply rate, independent of
   message quality.

2. **Even where a message is confirmed READ, replies are rare — 559 reads produced only 27 replied
   rows (4.8% read-to-reply), and even including quick-reply taps, only 18 of those 559 reads
   became a button tap (3.2%).** This points to the CONTENT/CTA, not just deliverability — CLAUDE.md
   §6f documents that the marketing-primary invite blast is the only template intended to carry a
   strong CTA, with everything else meant to funnel through a universal "Know More"/"और जानें"
   quick-reply. 18 of 45 in-window inbound messages (40%) from the 22 responders WERE quick-reply
   taps (mostly "Refer & Earn" / "Talk to advisor" / "Know More"), which is consistent with the
   funnel design working when a message is actually read — the bottleneck is upstream of read/reply,
   at delivery.

3. **Click-through on the referral link itself is nearly invisible to Wati.** All 39 distinct
   templates carrying a "Share on WhatsApp" / referral-link URL button have
   `isUrlBtnClickTrackingEnabled=false` (section b), so Wati cannot see when a recipient taps
   that button at all — GoRefer's own `share_intent` event (19 in-window) is the ONLY signal for
   that specific interaction, and it is markedly lower than the 34 raw `/r/` click events, which
   include OTHER traffic (referrer-shared links opened by a THIRD party, not the template
   recipient tapping their own button). The apparent "low interaction" partly reflects a
   measurement gap, not necessarily low real engagement with the link itself.

3b. *(supporting, same evidence pool as #3)* Session-window data (section c) shows only 4 distinct
   24h windows opened via the follow-up engine's own bookkeeping across the whole 7-day window —
   an order of magnitude below even the 22 replied-numbers — suggesting most "replies" the broadcast
   API sees are single one-off messages that don't register as a sustained conversation window at
   all, consistent with low sustained engagement rather than a single broken funnel step.

### Response-mode classification method (for T-032 reuse)

1. Pull `getMessages` for every number with a `status=replied` broadcast-recipient row in the window.
2. Filter to `eventType="message"` items with `owner=false` (customer-originated) whose `created`
   timestamp falls inside the study window.
3. Extract the quick-reply button label set from `templates_full.json` (`buttons[].type=="quick_reply"`
   → `parameter.text`). Case-insensitive exact match on the inbound `text` → `quick_reply_button`.
4. Else, match a 6-character letter-start alphanumeric string (the `client_id` format,
   `apps/referrals/validators.py`) → `keyword_trigger`.
5. Else → `free_text`.
6. URL-button taps are not observable at all (see finding above) — do not attempt to classify them
   from `getMessages`; use GoRefer's own `share_intent` event instead.
